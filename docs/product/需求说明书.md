## 一、功能说明与首期边界

平台服务于研发团队，将项目里程碑、团队任务、个人工作、临时需求、周计划和周报连接起来，帮助看清工作安排、实际进展与变化原因。团队按项目和周次统筹，个人按自己的节奏组织工作，不要求个人空间采用周视角。

当前团队共7人，包括负责人、4名后端和2名前端；后端两个组、前端一个组，通常一名老员工带一名新员工。现行做法是在当周最后一个工作日整理工作和下周安排，通过短会协调前后端分工。平台保留轻量研发小组，承担人员协调职责；任务、里程碑和汇报以项目为主线。

首期业务范围包括团队及角色、项目与里程碑、团队任务及个人任务、人员分工、周计划、进展和阻塞、开始结束时间、预计投入、周报、通知、交接和归档。

明确不纳入首期：

- 计时器、暂停恢复计时、并行计时、实际工时和重叠时长统计；只记录实际开始及结束时间。
- 新建自定义角色；采用权限可配置的预设角色。
- 多层子任务；团队任务只允许一层子任务，个人任务仅提供一层检查清单。
- 小组草稿确认流程、个人待整理业务状态、临时接任及专门的交接状态跟踪。
- 强制容量审批、依赖任务自动限制开工或自动调整排期。
- 专门的任务去重和合并能力；重复事项先用已有取消、关联调整方式处理。
- 单独的非工作日补记功能；使用统一补记方式。
- 个人任务及检查清单的回收站、删除恢复；专门的周报文件导出；区间投入估算。
- 文档平台联动，包括专门的文档关联、内容读取、创建、更新和同步，以及语雀文档迁移。
- 现有个人工具数据迁移；从新任务开始使用，必要的未完成事项手工补录。
- 网页及桌面端内置Agent聊天助手；首期由外部Agent调用系统业务能力及Skill。

首期提供网页、Agent能力和Windows桌面端，共用业务数据与权限规则。保留现有个人微信及群聊沟通，通过聊天中的链接进入适配手机的网页办理业务。微信聊天内直接与助手交互是后续优先方向，不纳入首期交付。飞书仅作为团队独立使用的协作文档工具，任务及执行状态由本系统管理；新项目试用飞书，现有语雀文档暂时保留，首期不做文档联动。本说明书不指定技术实现。

## 二、业务流程

### 2.1 团队初始化与项目建立

1. 超管先创建账号，再建立团队并从已有账号中指定团队负责人（界面称“团队管理员”，沿用同一身份）。
2. 团队负责人为没有账号的成员创建账号，已有账号直接关联；同一人保留一个账号。团队成员可以包含研发、项目经理等角色。
3. 团队负责人维护轻量小组、组长及成员，建立项目并指定项目经理、项目研发负责人和研发人员。
4. 首期一个人只属于一个团队，可以参与本团队多个项目；一个项目只归属一个团队。
5. 项目研发负责人或团队负责人根据建设方案建立里程碑。已知需要做但尚不能排期的事项放入未规划区。

团队及账号管理采用列表、搜索与明确行操作，新增和编辑使用弹窗。已有团队关联或业务记录的账号禁止删除，使用停用保留历史；仅剩管理员、无小组、项目或业务历史的空团队允许删除，管理员账号保留并解除团队归属。

### 2.2 从规划到每周执行

1. 组长从项目里程碑、待安排事项及未完成分工中编排下周初稿，协调本组跨项目工作量。
2. 团队负责人和各组长协调人员、工作内容及周目标。前端等协作需求可以先记为待分配。
3. 各组在同一份团队周计划草稿中整理本组安排，由团队负责人统一发布，保留发布基线；允许有待分配事项，不设置小组确认流程。
4. 成员可以直接在本人团队分工上开始、更新进展和完成自己的部分，也可以拖入个人空间，生成关联个人任务并自行组织执行。
5. 关联个人任务全部完成后，提示本人确认其团队分工是否完成；不按个人任务数量自动结束团队分工。
6. 任务主负责人判断整体完成后结束团队任务；里程碑负责人另行确认阶段目标完成。个人待整理事项不使团队任务自动恢复。
7. 系统生成一份团队周报草稿，组长按本组范围筛选、整理，按同一团队任务汇总展示。团队负责人直接调整并发布，不维护各组确认状态。

### 2.3 新增需求与临时工作

| 来源 | 进入方式 | 后续安排 |
| --- | --- | --- |
| 项目经理提交需求 | 默认由项目研发负责人接收，团队负责人可代为处理；可要求补充、暂缓或拒绝。 | 接收时必须指定任务主负责人，一条需求形成一条待安排团队任务，需要时再拆子任务；由组长安排本组人员、团队负责人统筹，接收不代表承诺本周完成。 |
| 研发成员创建团队任务 | 可在本人参与项目直接创建正式任务，无需审批；创建者默认担任任务主负责人，初始待安排。 | 可以推进、认领，但不能自行分配他人或改变团队承诺；不因创建而自动排入某周。 |
| 成员先发生的独立工作 | 可以先建个人工作、先执行，保存时必须选择项目，不强制建立团队任务。 | 需要协调时提交接收，或关联同项目已有团队任务；独立工作仍进入周报草稿。 |

“项目经理提交需求”和“研发成员直接创建任务”是不同业务入口。同一人兼任角色时，按所执行操作及权限处理，不要求其自行提交、再自行审批。

接收需求时，由接收人指定一名符合3.1人选范围的任务主负责人，可以选择符合条件的本人；未指定不能完成接收。指定任务主负责人不等于分配执行人员，也不自动产生人员分工或周安排。一条需求接收后形成一条团队任务，保留来源需求与任务的关联，需要拆分时按4.1建立团队子任务。

暂缓的需求可由有接收权限的人恢复处理。被拒绝的需求允许提交人补充后在原需求上重新提交，重新进入待处理，保留此前提交内容、补充内容和处理历史；重新提交不等于自动接收。要求补充、暂缓和拒绝均不产生正式团队任务。

需求尚未接收时，提交人可以修改内容，系统保留修改记录，接收人以最新内容处理。提交人也可以撤回尚未接收的需求，保留已有内容与处理记录；撤回后不再作为待处理需求接收，需要时可在原需求上重新提交。修改内容本身不代替被拒绝或已撤回需求的重新提交。

需求已经接收后，提交人可以追加说明，但不能通过修改原需求或撤回操作直接改变已接收的团队任务。追加说明不自动覆盖任务描述或完成标准，由任务主负责人确认后按现有权限更新任务；涉及新增范围的内容仍另提需求，不通过补充说明扩大原任务范围。追加内容及任务实际变更分别保留记录。

## 三、角色、组织与权限

### 3.1 角色与作用范围

首期采用固定预设角色及操作权限，不提供角色新增或权限配置。团队负责人负责本团队范围内的角色分配，创建项目时指定项目角色，不能借此扩大自己的授权。团队及项目作用范围、私人事项仅本人可见、个人执行事实不可代改等边界始终生效。

一个人可同时是项目经理、项目研发负责人、组长和团队负责人。有效权限按角色及作用范围合并，项目角色不自动获得其他项目或全团队权限。任务主负责人是具体任务上的责任身份，不等于项目研发负责人。

| 角色或责任身份 | 默认职责和范围 |
| --- | --- |
| 超管 | 管理入口仅为账号管理和团队管理：全局账号增删改查、启用停用和密码重置；团队增删改查、指定及更换团队管理员。不进入团队内部的小组、项目及任务业务。 |
| 团队负责人 | 管理团队成员和小组、分配团队内角色、建立项目；统筹跨组分工、调整任意组的周安排；维护里程碑、代为接收需求、发布计划和周报、处理交接及跨项目任务转移。 |
| 研发组长 | 分配和调整本组人员，整理本组跨项目计划及周报，管理本组工作归属；跨组需求交对方组长或团队负责人处理。 |
| 项目经理 | 提交需求和人选建议、提出规划调整、查看所负责项目全部团队任务及团队侧进展；默认不能分配研发人员或直接维护里程碑。 |
| 项目研发负责人 | 接收项目需求、维护里程碑、协调研发和跟进整体进展，指定或更换任务主负责人。可以不是组长；未兼任组长或团队负责人时不能直接分配人员。 |
| 研发人员 | 查看本人参与项目的全部团队任务、分工和团队侧进展；创建团队任务、认领本人工作、维护个人任务和执行记录。 |
| 任务主负责人 | 维护任务描述、完成标准和整体进度，创建团队子任务、负责整体结束；拥有约定的重开、取消、删除权限。默认不能更改已发布人员安排、周目标或交付日期。 |

除成员创建任务时默认成为主负责人、子任务默认继承父任务主负责人外，指定或更换任务主负责人由项目研发负责人、团队负责人操作。人选可为项目内任意研发成员；单独的组长身份不附带该权限。

### 3.2 轻量小组与项目成员

成员可以同时属于多个小组。小组维护成员、组长和人员协调权限，用于查看本组跨项目安排；每条人员分工可指定一个负责小组，由该组长安排和调整；也可选择“团队直属”，由团队负责人统筹，无需先加入小组。其他所属小组的组长可以查看，但不因此获得该分工的调整权限，团队直属分工也不按执行人的所属小组回退授权。跨组及直属与小组之间的归属调整须同时具备原、新归属的管理权限。负责小组属于人员分工，不要求整个团队任务归属某个小组；一个项目可以使用多个小组的人员。多组成员的工作量、周计划和周报按同一分工及来源工作去重，不因多组身份重复计算或汇报。

有分配权限的人可以选择尚未加入项目的团队成员：组长限本组，团队负责人可从全团队选择。分配时自动加入项目，任务可先保留“需要前端、待分配”。

### 3.3 查看与编辑边界

| 身份 | 工作事项查看范围 |
| --- | --- |
| 团队负责人 | 全团队工作事项及个人工作明细。 |
| 组长 | 本组成员工作事项及个人工作明细。 |
| 项目研发负责人 | 本项目个人工作，包括未关联团队任务的独立工作。 |
| 项目经理 | 本项目团队任务和提交到团队侧的进展，不因该角色查看个人任务明细。 |
| 研发人员 | 本人参与项目的工作任务，以及本组成员的工作任务；可以查看任务明细，包括独立或关联的个人工作任务。 |

首期按工作任务管理，普通研发人员在上述范围内也可以查看任务明细，不再额外区分“团队摘要可见、个人工作明细不可见”，不增加针对普通研发人员的明细级权限。查看不等于可以修改他人任务。私人事项始终仅本人可见，不进入团队周报；无关团队或项目不因此开放。同一人兼任角色时查看范围合并，项目经理单独角色的查看范围仍按上表执行。

个人任务内容、状态及实际开始结束时间仅本人修改。管理者可以调整团队分工、关联归属和周报表述，不能代改个人执行事实。整体结束、取消、转交等动作可以限制关联工作继续执行，但不能伪装成本人确认完成。

## 四、功能说明与关键规则

### 4.1 对象、关联与拆分

任务界面参考Trello的看板交互：横向列表承载任务卡片，支持列表内拖拽排序、列表间移动和点击卡片查看详情。卡片突出标题、负责人或参与人、日期及必要状态；完整说明和业务操作在详情中呈现。借鉴交互方式，不照搬Trello的业务模型或全部功能；团队看板固定为“待开始、进行中、已完成”，取消任务通过筛选查看，“待分配”独立表达，不与执行状态混用。个人空间支持自定义分类列表，分类与执行状态独立，移动分类不改变执行状态。团队卡片跨状态列移动执行对应业务操作，按卡片对象检查权限、状态条件和必要确认，不将完成本人分工与团队整体结束混为一谈；阻塞保持独立标记。

任务卡片提供开始、结束快捷入口，按卡片代表的对象、当前用户权限和执行状态展示，对应既有开始、完成本人分工或整体结束操作。快捷操作与详情页遵守相同规则；结束时保留必要确认，不代改他人的个人执行事实。

任务说明（描述）和完成标准均为选填，不作为创建、开始或结束任务的必填条件。未填写或仅含空白时，详情不展示对应标题、内容或占位区域；编辑任务信息时可补充或清空，保存后按实际内容展示。编辑权限及其他结束条件保持原有规则。

| 对象 | 含义 |
| --- | --- |
| 项目 | 团队工作归集单位；公共研发、内部学习等可作为普通项目，不增加跨项目投入分摊。 |
| 团队任务 | 共同工作及整体结果，有一名主负责人、多名参与人，可进入里程碑和多周安排。 |
| 人员分工 | 某个人在团队任务中的责任、工作内容和执行情况；每周可分别安排，不等同于个人任务。 |
| 个人任务 | 本人独立管理的执行事项，可关联团队任务，也可独立存在；私人事项与工作事项区分。 |
| 团队子任务 | 团队工作的执行拆分，只允许一层；拆分后的父任务负责汇总和整体结束。 |
| 个人检查清单 | 个人任务内的一层条目，仅记录内容和勾选结果，不另设负责人、开始结束时间或状态联动。 |
| 里程碑线 | 按项目预计完成日期组织建设事项，含未规划区。 |
| 周计划 | 团队某周安排，保留发布基线、人员分工及后续调整。 |
| 周报 | 对归属该周的实际工作、原计划推进情况及新增事项的汇总。 |

里程碑是独立的阶段目标，创建时不自动生成团队任务。一个里程碑可关联多条同项目团队任务，每条团队任务最多关联一个里程碑，也允许不关联。创建任务时可选择关联，已有任务由主负责人或有里程碑维护权限的人调整关联。拆分子任务默认沿用父任务关联，后续可单独调整；跨项目转移解除原项目关联。跨周沿用原任务，不创建同名副本。个人任务与团队任务的关联不属于父子层级。

一条可执行的团队任务可关联多条个人任务；一条个人任务只能关联一条未拆分的团队任务或一个团队子任务，关联子任务后在父任务汇总展示，不重复归集。个人标题、清单、排序、排期独立，不覆盖团队原任务。拆分后的父任务不再直接承接新的个人执行工作。

个人检查清单不作为独立任务分配、排期或汇报，也不自动完成个人任务或团队分工。需要独立安排的工作新建另一条个人任务，可关联同一团队任务。

组长可将本组独立个人工作直接关联到同项目已有团队任务，保留个人任务和执行记录、通知本人，不另复制工作。任务转移项目见4.11。

父任务主负责人、项目研发负责人、团队负责人可创建团队子任务，默认继承父任务主负责人。普通参与人可提出拆分建议，或整理本人的个人任务及检查清单。创建子任务不赋予分配他人的权限。

没有子任务时，团队任务可直接安排执行；有子任务后，人员分工、周计划和预计投入只安排在子任务，父任务保留主负责人、规划日期及整体进度，负责汇总和整体结束。联调、协调等工作也作为子任务安排。

已有执行安排的任务再拆分时，必须将当前及后续执行安排移至子任务，尚需执行的个人关联工作同步调整到对应子任务；分配调整仍由有相应权限的人处理。原执行记录、已发布基线和历史周报保留，记录拆分及迁移关系，不复制一份历史投入到子任务重复汇总。

全部团队子任务完成后，只提示父任务主负责人确认，不自动结束父任务。整体进度不按子任务数量自动计算。子任务日期晚于父任务时提示冲突，由团队负责人或项目研发负责人决定是否调整父任务日期，不自动顺延。

### 4.2 项目与里程碑

里程碑界面采用鱼骨图组织独立阶段目标：按预计完成日期连接时间主轴，同日允许多个目标，并保留“未规划日期”区。点击目标展示关联任务及完成数量，关联任务可打开任务详情。任务进展仅作参考，不按任务数量自动计算目标完成状态。

新建目标录入名称、负责人及可空的预计完成日期，不录入任务说明或完成标准。日期由所选日期组带入；当前用户具备项目研发成员资格时默认本人负责，否则默认项目研发负责人，可选择其他可用项目研发成员。负责人单独确认目标完成，完成前展示尚未完成的关联任务；关联任务全部完成也不自动完成目标。重新打开须填写原因。里程碑管理者可维护名称、负责人、日期及移出目标，移出解除当前关联并保留全部任务、分工和执行历史。

每个项目通常有一条里程碑线，立项时以建设方案为主要来源。团队负责人、项目研发负责人可以新增建设事项、维护预计完成日期，其他人提出调整建议。项目研发负责人不必兼任组长即可维护规划。

近期滚动安排约一个月，远期允许模糊。节点日期表示预计完成日期，同日可有多项事项。“未规划”表示已知工作但尚未确定日期，例如等待外部条件，不意味着计划外。条件成熟后移入近期安排。

里程碑日期调整保留原日期和原因，不修改任务自身日期或执行状态。关联已发布工作的明确交付日期变化仍须团队负责人确认。执行中新增要求单独记录并关联原任务，不能直接扩大原任务范围；计划外标签按4.7人工维护。

### 4.3 分配、认领、退出与转交

组长只分配本组人员，并按3.2维护由本组负责的人员分工；不能因成员同时属于本组而调整其他小组负责的分工。团队负责人可以跨组分配并调整任意组安排，也可分配、调整团队直属工作。项目研发负责人提出人员需求；兼任组长时可直接分配本组，不增加自我审批。

分配后立即生效并通知本人，不必逐项接受。不拖入个人空间不取消团队责任。成员可提出调整或说明阻塞，不能自行更改团队排期和交付目标。

成员可在本人参与项目直接认领尚未分配的工作，立即生效。认领时可指定本人所属的一个小组，也可选择“团队直属”；分别通知负责小组组长或团队负责人。认领只建立本人分工，不自动成为任务主负责人，不自动改变排期或交付目标。

认领不要求选择周次，也不自动进入当前或未来的周计划，由组长或团队负责人另行安排周次。成员可以先执行，实际发生的工作按汇报归属周进入周报草稿，不以已纳入周计划为前提。

| 分工来源 | 退出规则 |
| --- | --- |
| 自行认领 | 可直接退出，填写原因并通知该分工负责小组的组长，团队直属则通知团队负责人；未完成工作恢复待分配，保留已发生记录。 |
| 管理者分配 | 不能自行退出，应提出调整，由组长或团队负责人处理。 |

两种来源明确展示并留痕。退出执行分工不能自动解除兼任的任务主负责人职责。

转交由有分配权限的人操作。保留原人员分工和记录，标记“已转交”，为接手人建立新安排。原人员关联个人任务保留在其空间，停止执行、允许补记和整理；接手人自行建立个人任务。转交时间单独记录，不冒充实际完成时间。

### 4.4 周计划、预计投入与调整

#### 编排与发布

团队每周维护并发布一份周计划，只有一份共同草稿，覆盖多个项目和小组，支持按项目、小组、人员查看。小组只是筛选和编辑范围，组长按权限整理本组安排，团队负责人可直接补充、调整、发布。团队直属分工照常进入周计划、未完成结转、工作量和周报汇总，可用“团队直属”筛选；仅团队负责人可整理这部分安排与汇报，成员仍只维护本人执行事实。不设置小组独立草稿、提交、确认或未确认提示。

允许带待分配事项发布，明确展示未落实人员的需求；发布不等于所有人员需求均已落实。后续补人记录变更，是否为周计划外由人工标记。

#### 按人安排及跨周结转

同一团队任务可按参与人分别安排工作内容和周次，工作内容选填。例如接口开发安排在本周，页面开发及对接安排在不同周。进入某周表示准备投入，不默认要求整项完成。

本周未完成工作自动延续到下周草稿，沿用原任务和人员分工，标注“上周延续”并保留来源周。只延续之前明确安排且当前仍有效的未完成分工及待分配任务；未曾安排的未来工作不进入周待办。已完成、已取消、已转交或已退出的原分工不带入；目标周已有安排不重复添加、不覆盖人工内容。周目标与预计投入重新填写，允许留空；进入草稿不构成正式承诺。

周任务默认本周，支持一键查看下周。“本周安排”仅展示所选周已安排且仍可执行的分工；尚未安排的工作单独放在“待安排”，完成及停止记录在安排与历史中保留。允许移出本周回到待安排，移出后不会因刷新再次自动加入，重新安排后恢复后续延续。已发布周计划和周报不自动改写；已发布目标周需人工调整草稿并重新发布。个人待办保持个人视角，不跨周复制。

有子任务时只在子任务安排人员、周计划及预计投入，父任务汇总展示，不另设执行安排。联调、协调等也创建子任务，避免父子重复估算。已有安排后再拆分按4.1迁移，已发布历史保持原样。

#### 目标、估算和工作量

周目标、预计百分比和预计投入均选填。预计投入只放在“每人、每周、具体分工”上，以天为单位填写单个数值，允许小数，例如0.5天、1天、2.5天，不填区间；个人任务不重复填写。展示每人跨项目安排，按数值求和预计投入，例如2.5天加1天显示3.5天。未填估算的事项单独提示，不能把合计当作全部工作量；不因超量阻止发布，由组长或团队负责人协调。

没有明确目标时，以实际工作、当前状态和阻塞反馈。不能因跨周未完成就判定延期，也不能以完成任务数除以计划任务数代表计划完成率。明确日期或承诺目标未兑现时，应说明偏差。百分比不替代完成确认，整体进度由任务主负责人维护，不按子任务数量自动计算；填写时区分累计进度与本周新增进度。

#### 发布后的调整

保留发布基线。组长可调整由本组负责的人员分工及其本周安排，团队负责人可调整任意组；记录新增工作和受影响的原安排。涉及跨组协调或项目明确交付日期变化时，由团队负责人确认。

个人可自由调整执行顺序和个人排期；影响团队期限或目标时提出调整，不能自行修改团队承诺。任务主负责人可以维护描述、完成标准，已发布人员安排、周目标、交付日期仍由有相应权限的管理角色调整。

### 4.5 个人执行、完成及收尾

独立个人工作保存时必须选择项目；私人事项不受该要求约束。无需计时或先建团队任务即可记录紧急工作，个人记录不自动构成团队排期承诺。

成员可以直接在自己的团队分工上点击开始、完成我的部分，也可记录工作内容、发生日期及进展，无需创建关联个人任务。团队分工和个人工作支持多条进展记录，每条分别保留实际发生日期、汇报归属周和进展内容，不只保存最新进展，不要求每日填写。周报按各条记录的归属周汇总当周实际工作，不用任务起止时间推断每周完成内容；同一工作通过团队分工与关联个人任务呈现时保留来源关系，避免重复汇报。

个人任务全部完成后提示本人确认团队分工完成，不自动确认。团队任务尚未结束时，新增关联的未完成个人工作会自动恢复该参与人为未完成，并提示本人。

本人重新开始关联个人任务时，相应团队分工恢复为未完成。解除关联或删除个人任务不自动将团队分工标为完成，仍由本人确认；团队任务已结束时须先按权限重开，不能通过个人操作绕过执行限制。

本人也可在存在未完成关联个人任务时确认团队分工完成：先提示未完成工作，确认后相关个人任务停止执行，保留本人原状态并提示“关联分工已完成”，不自动标记完成。不另设“待整理”业务状态。继续执行前恢复分工为未完成；团队任务已结束时先按权限重开。

任务主负责人可结束整体任务，无需所有参与人逐一确认，不增加独立验收审批。结束前提示未完成子任务、分工和关联工作，确认后统一结束该范围的团队工作、限制继续执行。测试和评审按需作为任务或子任务安排。

个人空间保留本人原状态，同时提示“关联团队任务已结束”，不将提示当作新的个人任务状态。允许本人整理已有内容、确认收尾、补记历史，已有检查清单条目可编辑、删除或勾选；不允许在已结束范围新增执行工作或继续执行。个人尚未整理不自动重开团队任务。

### 4.6 实际开始及结束时间

首期只有时间点记录，没有计时能力。点击开始、完成时自动记录实际开始、实际结束时间，允许本人补录修正。人员分工可以直接记录这些时间；团队整体结束时间与成员本人完成时间分别表达，不能由整体结束伪造个人完成。

团队任务、团队子任务、人员分工及个人任务的开始结束时间分别记录，不因父子或关联关系自动传播。状态变化按4.5处理，不自动填充另一对象的开始结束时间；个人检查清单不记录这些时间。

任务重开后保留首次开始时间，清空当前结束时间；再次完成记录新的结束时间。历次完成及重开记录保留。开始到结束之间可能包含等待、休息，不把时间跨度当作实际工时或人员利用率。

误点团队任务“开始”后，主负责人可撤销本次开始，任务回到未开始，清除误点产生的开始时间并保留操作历史。已有实际进展、时间修正或关联工作已执行时不能直接回退，具体边界见研发需求4.6。

实际发生日期和汇报归属周分别保留，不为调整汇报周期而修改真实日期。首期不提供耗时补填和实际投入统计；前期关于进展耗时选填、暂停恢复、并行计时、重叠计算及结束时停止计时的方案均已被本轮“只记录开始结束时间”取代。

### 4.7 手动计划外标签

首期完全手动标记，不根据创建日期、录入日期、加入里程碑或周计划的时间自动判断。发布基线和调整记录用于回看事实，不触发标签自动赋值。

| 标签 | 标记位置 | 默认维护角色 |
| --- | --- | --- |
| 里程碑外 | 直接标记在工作任务上，包括独立个人工作；关联任务保留具体工作标签，不给整条项目里程碑统一标记。 | 独立个人工作由本人或其范围内有管理权限的人维护；团队任务由团队负责人、项目研发负责人维护。 |
| 周计划外 | 直接标记在工作任务上，同时指定对应周次，不是任务永久标签，也不要求先建立周安排。 | 独立个人工作由本人或其范围内有管理权限的人维护；团队任务由团队负责人、负责该工作安排的组长维护。 |

独立个人工作记录时即可由本人顺手标记，无需先关联团队任务或纳入周计划。有查看权限不等于有权修改他人的标签。

两个维度独立，同一任务在不同周可采用不同的周计划外标记。晚录入不等于计划外，早已录入也不等于本周计划内。未标记就是未标记，不要求逐项确认成计划内；首期仅统计已人工标记的计划外事项，不做完整的计划内外占比，也不把未标记事项统计为计划内。没有预计日期或尚未关联里程碑不自动标记计划外。

关联个人工作按对应团队工作归集，不能因为个人拖入、排序、正常拆分而改变标签。新增要求单独记录，是否计划外由具有上表权限的人手动判断。独立工作后续建立关联时保留原标签及变更记录，不自动覆盖团队任务标签；周报整理时由有管理权限的人统一归集，避免重复统计。标签和归属调整保留记录，当前变更不自动改写已发布周报。

### 4.8 周报、周期与补记

#### 生成及汇总

系统根据团队侧个人进展、关联个人工作和独立工作生成一份团队周报草稿，包括归属该周的实际工作、本周发布计划中未开始或未完成的任务；私人事项不进入。

各组在同一份草稿中筛选、整理本组人员工作，不维护独立组报及其确认流程。团队视图按同一团队任务汇总，保留人员和各组进展，不能因多人、多条个人任务或父子层级重复上报。周报反映本周做过什么，不能仅依据任务当前是否完成生成。

组长在本组范围内可调整表述、合并零散汇报或排除不适合内容。团队负责人可直接整理、发布，不要求各组或个人逐一确认，也不展示小组确认状态。汇报表述的修改不改动原始执行记录，原记录有误由本人修正。

再次生成周报草稿时保留人工修改、合并和排除结果，只补入尚未纳入的新工作，不重复加入已有工作。已整理事项的源数据发生变化时，提示有整理权限的人处理，不自动覆盖人工表述；已人工排除的事项不自动加回。此规则不改变已发布周报，已发布内容仍按修订规则处理。

#### 整理时间与归属周

周次按周一至周日标识，通常在当周最后一个工作日整理计划和周报，节假日按实际安排调整，不固定要求周五发布。标识周的日期范围不限制实际整理和发布时间。工作默认归实际发生日期所在周，非工作日工作可按实际情况改归上周或下周。

实际发生日期与汇报归属周区分。非工作日归上周的工作使用统一补记，不另建专门功能；首次使用的计划外标签也由人工判断，不按导入时间推算。

本人在录入或补记时可以修改汇报归属周，组长和团队负责人可在管理范围内调整汇报归属，不修改真实发生日期。周计划、周报草稿按需生成，首期不设定时生成流程；下周初稿生成时按4.4带入未完成分工。已发布内容仅通过修订改变，不因归属调整或重新生成草稿被自动覆盖。

#### 发布与修订

补记保留真实发生日期并归入所选汇报周。已发布周报出现补记时提示，团队负责人可选择修订并重新发布，旧版本保留；不要求每次补记都重发，也不自动改写历史。当前任务归属、计划外标签和项目转移同样不改写历史周报。

首期周报在页面按项目组织“本周工作＋下周安排”，支持一键复制文字，方便粘贴到聊天或语雀；不做Excel等专门文件导出。

已发布周报向本团队全体成员公开，包括整理后的人员进展及跨项目汇总；项目经理可以查看这些正式汇报内容。草稿及原始任务、进展记录仍按既有权限访问，公开周报不授予源记录访问权。私人事项始终不进入周报。复制已发布周报文字遵循同一公开范围；成员移出团队后失去原团队周报访问权限。

### 4.9 生命周期：结束、重开、取消、删除

| 操作 | 默认权限 | 主要规则 |
| --- | --- | --- |
| 整体结束 | 任务主负责人。 | 提示未完成工作后确认结束；保留个人尚未自行确认状态。子任务全完成不自动结束父任务。 |
| 重开 | 任务主负责人、项目研发负责人、团队负责人；其他参与人提出请求。 | 填写原因，保留结束历史，不自动纳入本周安排；继续执行按当前分工处理。 |
| 取消 | 任务主负责人、项目研发负责人、团队负责人。 | 填写原因并通知参与人；保留工作记录，关联工作停止执行、允许收尾，不标记完成，不自动结转下周。该周已做工作仍入草稿并注明取消。 |
| 删除 | 与取消相同。 | 仅限没有执行记录、也未进入已发布计划或周报的任务；误开始已撤销且没有其他执行事实的任务可删除，开始与撤销历史仍保留。删除只需确认影响，不要求填写原因；其他情况取消或归档。有子任务或关联个人任务时先处理关联，不连带删除他人记录。 |

任务重新出现原范围内遗漏工作时可以重开；新增需求另建任务并关联原任务。首期不建设专门的重复任务合并或去重机制。

个人任务和检查清单条目由本人删除，操作前确认、不要求填写删除原因；首期不提供回收站或删除恢复。删除不自动完成团队分工，也不连带删除团队任务。已发布周报保留发布时内容，不因原个人任务或条目删除而消失；历史引用不能要求原记录仍可打开才能查看发布内容。

### 4.10 阻塞与任务依赖

阻塞是独立标记，记录原因，等待对象选填，不强制填写进度。分别表达人员分工受阻和整条团队任务受阻，互不自动联动；默认操作本人分工，整体受阻需单独标记。

团队任务主负责人和参与人可标记、解除团队任务阻塞，记录操作人并通知主负责人。个人任务阻塞仅本人维护。

用阻塞原因、等待对象和关联任务表达依赖，不以依赖未完成限制开工，不自动调整排期。关联的等待任务完成后通知受影响人员，由人工确认解除阻塞，不自动解除；仅有文字说明的阻塞同样人工处理。

### 4.11 项目转移与归档

团队负责人可在本团队内跨项目转移任务，关联子任务及个人工作同步调整归属，保留原归属和转移记录，不改动个人执行内容和时间，不改写已发布周报。

任务主负责人和当前参与人自动加入目标项目，保留分工并通知本人；只存在历史记录、已经退出或转交的人员不自动获得目标项目权限。转移前提示关联工作将按目标项目权限开放查看，避免只移动任务却遗漏访问范围变化。

项目归档由团队负责人或项目研发负责人操作。归档前处理未结束团队任务及独立个人工作：完成、取消或转移后再归档。已停止执行、只待个人整理补记的事项不阻塞归档。管理者不能为满足归档条件代改个人完成记录。

归档项目保留历史查询和周报，不新增工作、不进入新周计划。有后续需求时先恢复项目。

### 4.12 成员移出与交接

首期人员只能属于一个团队，更换团队走转移，账号保留。允许先移出成员，同时列出其未完成工作和管理职责，由团队负责人协调有权限的人手动转交、取消或更换负责人。清单基于尚未处理的工作及职责展示，不新增“待交接”状态、交接审批或独立交接跟踪流程。移出人员的原分工不能继续作为其正常执行安排结转。

移出后立即失去原团队访问权限。原团队工作任务和记录留在原团队，本人及新团队不能访问，私人事项仍归本人。原团队历史记录不因账号转移被删除或改写。

管理职责使用现有负责人及角色分配操作手动替换，不提供临时接任身份或批量临时授权。团队负责人由超管指定替换，其他职责由团队负责人按权限处理。保留角色和分工变更记录；更换管理负责人不自动承接全部执行工作。

### 4.13 总览与通知

团队总览默认按项目展示周安排、进展、计划变更、待分配及阻塞，再按人员查看跨项目分工和预计投入。未估算的工作明确提示，不用任务数或时间跨度判断谁更忙。

| 触发 | 通知或提示对象 |
| --- | --- |
| 分配、转交、取消、整体结束及重要排期变化 | 受影响成员。 |
| 参与人确认完成、团队阻塞变化 | 任务主负责人；分工阻塞按协作需要提示相关人员。 |
| 直接认领、自行认领退出 | 该人员分工的负责小组组长；团队直属分工通知团队负责人。 |
| 管理者建立个人工作关联、跨项目转移 | 相关成员。 |
| 新增未完成关联工作使本人状态恢复 | 本人。 |
| 等待的关联任务完成 | 受影响人员，提示确认解除阻塞。 |
| 已发布周报新增补记 | 提示团队负责人决定是否修订。 |

首期仅提供业务事件通知，按上表及既有流程中的待确认事项通知对应人员；不建设评论、@提及、手动催办及图片或文件附件能力。普通编辑、个人排序和日常拆分默认不通知他人；影响协作的变化按上表处理。

同一用户在网页和桌面端共用通知记录及已读状态；任一端标为已读后，另一端同步显示已读。网页展示站内通知，桌面端额外提供Windows系统通知；同一事件在同一桌面端不重复弹出系统通知，不因重连或重复接收形成重复通知记录。系统通知的展示不等于用户已读。

### 4.14 使用入口与Agent接入

首期采用“微信沟通＋网页操作”：保留现有个人微信和群聊，用户点击聊天中的链接进入适配手机的网页，提交需求、补充信息和查看有权限的进展。业务操作在网页完成，多个入口共用同一份任务数据，并遵循相同身份与权限规则。链接的分享不代表接收者自动获得业务数据访问权限。此入口约定不代表已确定向个人微信或群聊自动推送通知，通知触达方式仍待技术验证。

后续优先考虑在微信聊天内直接与助手交互，包括自然语言新增更新任务、聊天消息转任务并保留来源、查询安排及按权限操作。该方向不纳入首期交付，不预设自动读取全部聊天，接入可行性和具体能力需选型验证。

首期提供网页、外部Agent接入能力和Windows桌面端三个入口。网页与桌面端的业务功能和操作保持一致，桌面端额外支持Windows系统通知；各端共用任务数据，不维护独立副本。

桌面端关闭窗口后驻留Windows系统托盘，继续接收通知；最小化窗口也不停止接收通知。用户可从托盘重新打开窗口，或选择“退出程序”完全退出。完全退出后停止接收新的系统通知，不要求程序退出后仍在后台接收。通知仅面向当前已登录且有权接收的用户，实际展示受Windows通知设置影响。

首期由超管或团队负责人创建账号，不开放自助注册。超管管理全局账号；团队负责人可创建并直接加入本团队的成员账号、关联未入团队的已有账号、启用停用和重置本团队其他成员密码，不能操作本人、超管或其他团队账号。账号登录名与姓名的编辑、账号删除由超管处理。采用账号密码登录，本人修改密码须验证旧密码，且新密码不能与旧密码相同。网页和桌面端均联网使用，不提供离线编辑及后续同步；本轮交付在Windows本机运行，正式服务器及公网部署不在本轮交付范围。

首期由用户在已有外部Agent工具中调用系统提供的业务能力和Skill，网页与桌面端不另建聊天助手。系统提供接入能力、使用说明和常用场景Skill；认证采用用户自行生成的个人访问Token，首期不建设OAuth授权流程。首期兼容目标为Codex、ZCode、Qoder、Workbody，本轮只要求Codex实际接入验证，其他三者保留兼容目标并标记未验证，不阻塞本轮验收；具体版本、接入协议及Skill交付方式在技术方案中确定，不据此承诺兼容所有外部Agent工具，也不代表四者已完成接入验证。

除个人Token管理外，Agent覆盖网页提供的全部业务查询与操作，不限于任务查询、新增和更新。网页上的拖拽、点击等交互，Agent应能完成等价的业务结果，不要求逐步模拟界面动作。例如网页调整周安排，Agent也能按相同规则完成调整；网页支持的管理操作同样按调用者权限开放。

Agent遇到需要确认的操作时，先向用户展示操作内容和影响范围，用户在Agent对话中确认后提交，无需跳回网页确认。确认绑定具体操作及当时的数据版本；提交时相关数据或影响范围发生变化，应重新展示并确认。服务端仍校验权限、业务状态及确认是否适用于本次操作，不能仅依赖Skill提示词。

Agent按对应用户身份和权限执行，记录操作归属；网页要求填写的必要信息、满足的状态条件和执行前确认，Agent同样遵守。用户以Agent操作本人的记录仍属于本人操作，管理者不能借Agent代改他人的个人执行事实。执行结果应明确成功、失败及原因，不能把仅生成建议或草稿表述为已经提交或发布。

用户通过网页登录或桌面端登录后，可在个人设置生成、撤销本人的访问Token，用于配置外部Agent。Token生成和撤销仅允许通过上述登录入口操作，不向Agent开放，也不能凭现有个人Token调用生成或撤销接口。这是Agent完整业务覆盖的明确例外。

Token直接代表所属用户，不再单独划分只读、读写或项目授权范围。每次调用均校验用户当前的角色、项目范围和业务操作权限，不固化生成Token时的权限；用户被移出项目后不能凭原Token继续访问该项目，账号被禁用后不能继续调用。Token不替代业务操作本身的必要信息、状态条件及确认要求。

生成Token时由用户自行设置有效期，可选择到期时间或“永久有效”，不固定为90天。选择永久有效时显示明确提示：“此Token不会自动过期，拥有它的人可在你的当前权限范围内调用系统。泄露后可能被持续使用，请妥善保管，不再使用或疑似泄露时立即撤销。”永久有效仅表示不按时间自动过期，不免除账号状态及权限检查。用户可以撤销本人的Token；到期或撤销后，后续调用应拒绝认证，不执行所请求的业务操作。

首期Skill面向项目经理和研发负责人，聚焦需求、团队任务和周报，将相关查询、信息补充和业务操作组织为可复用流程。暂不提供个人日常执行类Skill，例如编排本人工作、更新本人进展与阻塞；这不缩减网页功能及Agent对网页业务操作的完整覆盖范围。

首期需求类Skill支持项目经理整理、提交和补充需求、查询处理情况，并按2.3修改或撤回尚未接收的需求、重新提交被拒绝或已撤回的需求，以及追加已接收需求的说明；支持研发负责人查看待处理需求，并按现有权限要求补充、接收、暂缓、恢复处理或拒绝。团队任务类Skill支持查询项目任务、进展和阻塞，整理任务描述与完成标准，以及按现有权限创建或拆分团队任务。周报类Skill支持下文约定的汇总、整理和发布操作。Skill使用同一套Agent能力，不另建业务规则，不扩大权限或绕过必要确认。

首期不专门提供跨项目人员调度、周计划自动排期的Skill流程；网页已有的人员安排和周计划操作仍由Agent按相同权限与规则提供。

上述“研发负责人”在具体操作时按现有项目研发负责人、团队负责人等实际角色及作用范围校验，不新增同名角色。项目经理不因使用Skill获得人员分配权限；单独的项目研发负责人身份不因此获得团队周报编辑或发布权限。

周报类Skill保持现有权限：项目经理、项目研发负责人按指定项目和周次汇总本人有权查看的项目进展，生成汇报文字，不写入或修改团队共享周报草稿，也不视为正式发布。项目经理的汇总不包含其无权查看的个人任务明细。组长可按本组范围通过Skill整理共享周报草稿，团队负责人可整理全团队草稿并发布，遵循4.8的既有规则。兼任多个角色时按已有角色权限合并，不因使用Skill扩大权限。

### 4.15 协作文档与飞书定位

飞书仅作为团队独立使用的产品、需求、方案等协作文档工具，任务、人员分工、排期、执行状态和周报发布记录由本系统维护，不以飞书多维表格承载这些核心业务。文档正文在所属文档平台维护。

新项目试用飞书协作文档，现有语雀文档暂时保留。首期不建设文档联动，包括专门的文档关联、内容读取、创建、更新和同步，也不迁移语雀文档；Agent和Skill同样不包含文档平台联动能力。项目经理可以继续从微信链接进入系统，不强制将日常操作迁入飞书。后续是否建设文档联动另行评估，不作为首期交付前提。首期不迁移现有个人工具数据，从新任务开始使用，必要的未完成事项按现有任务规则手工补录。

## 六、研发待细化事项

- 需求接收、内容修改、撤回及重新提交按2.3执行；技术实现需防止修改或撤回与接收并发时使用旧内容接收、接收已撤回需求或重复生成团队任务，操作结果应反映实际生效的状态。
- Q01（入口、Skill范围及迁移边界已确认）：Agent采用外部工具接入及个人访问Token认证，不单独划分Token权限；有效期由用户设置，支持永久并提示风险。首期不建设网页或桌面内置聊天助手，也不建设OAuth授权流程。技术方案需确定Codex、ZCode、Qoder、Workbody的兼容版本、接入协议、Token生成存储与校验实现及Skill交付方式，本轮完成Codex实际接入验证，其他三端保持未验证；同时细化网页登录与链接访问、Windows桌面技术及通知实现。桌面端关闭窗口驻留托盘继续接收通知、显式退出后停止接收的行为已确认。后续微信聊天助手另行验证接入可行性。
- 需求、团队任务和周报类Skill按4.14已确认的操作范围与权限实现。逐项核对网页业务能力与Agent能力的覆盖关系，包括管理操作、必要信息、权限、状态条件、确认步骤及执行结果，不能仅提供查询和基础任务增改就视为完整覆盖。
- 固定角色权限与作用范围统一校验，明确预设角色权限、项目身份、任务责任和个人记录不可代改之间的关系；所有入口执行同一规则。
- 团队任务、子任务、人员分工、每周安排和个人任务独立表达，避免关联和汇总导致重复复制或覆盖。
- 区分完成、统一结束、取消、转交和退出；关联工作结束等提示及执行限制不新增个人业务状态，不伪造本人完成或结束时间。成员交接使用待处理清单及现有调整操作。
- 个人检查清单仅维护内容和勾选结果，不承担独立任务的权限、时间、排期、汇报或状态联动。
- 周计划基线、手动标签、项目归属、交接和周报版本可回看，不被当前状态覆盖。
- 并发分配、认领、转交和个人补记不能丢记录；成员移出与项目转移同步处理访问权限。
- 拆分后仅子任务承载执行安排；迁移当前安排与保留历史基线分别处理，不重复汇总父子或关联工作。实际时间跨度不用于计算实际工时。
- 重复拖入同一团队任务时提示已有关联，允许有意义的多条个人任务；具体交互防止误建重复项。
